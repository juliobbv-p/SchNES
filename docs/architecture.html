SchNES Architecture

Introduction

SchNES emulates the NTSC Nintendo Entertainment System and the Famicom Disk System. Its core runs 6502 instructions in batches between hardware deadlines. When an interrupt, DMA transfer, or timing-sensitive register access requires attention, the core advances the affected devices to the relevant cycle.

This timing model connects the ARM64 recompiler, scanline renderer, and fixed-point audio mixer. Regular and Ultrafast use different rules for when work can be deferred. The SDL frontend handles controller input and presentation, with optional runahead to show the effect of fresh input sooner.

Machine state and the frame boundary

The C core keeps CPU, PPU, APU, controller, bus timing, and cartridge or disk state in a Nes instance. The SDL frontend loads media, supplies controller state on demand, advances the machine, and presents its output. The headless driver uses the same core frame entry point.

The PPU counts the new frame at vblank. Video and audio are buffered in the core, so host texture upload, cropping, audio queueing, and display pacing live outside CPU execution.

How devices share time

CPU cycles form the scheduler’s timeline. The PPU advances three dots per CPU cycle in the emulated clock domain. The audio sample clock maps elapsed APU time to 48 kHz output. The bus stores a deadline for when the CPU fast path must reconsider its next action.

The core distinguishes the next PPU event from the next PPU event that can affect the CPU. Write classifiers tell the dispatcher and recompiler which registers can change the raster, IRQ line, deadline, PRG mapping, audio, or cached code. The bus handler applies writes that require the shared timed path. Pending OAM DMA and controller strobe transitions can narrow the fast-path window to one cycle.

Example   A scroll change at a HUD split

In a typical split-screen routine, the CPU reads $2002 until a status bit changes, then writes scroll or address registers. The CPU-visible status read must reflect the relevant PPU dot. The subsequent write can change how future pixels are drawn, so the PPU applies it at its effective time. Completed work before the split can remain cached when its inputs still match.

CPU execution and native traces

SchNES uses several ways to execute 6502 instructions. Within a safe window, the core can dispatch directly, batch recognized loops, or enter an ARM64 trace. Near a boundary it can step timing-sensitive instructions individually. An instruction started in the fast dispatcher can finish through the shared bus handler.

Example   Four accumulator shifts shrink from 32 to 12 bytes

Original 6502 code. Four one-byte instructions shift the accumulator four bits to the right.

lsr a
lsr a
lsr a
lsr a

ARM64 emitted one shift at a time. This two-instruction sequence repeats four times. w4 holds the guest accumulator and w16 holds the pending carry.

ubfx w16, w4, #0, #1    // Save the bit shifted out
ubfx w4,  w4, #1, #7    // Shift the 8-bit accumulator right

Optimized ARM64. Each shift overwrites carry. The fourth shift’s carry is bit 3 of the original accumulator, so the recompiler extracts it once and shifts the accumulator by four in one instruction.

ubfx w13, w4, #3, #1    // Extract the final carry from the original value
mov  w16, w13
ubfx w4,  w4, #4, #4    // Keep the original upper nibble

For example, $B8 becomes $0B with carry set. The trace still accounts for four guest instructions and eight emulated CPU cycles. It derives the final negative and zero flags from the result. The 32- and 12-byte counts cover the native shift body.

emit_shift_run() in the ARM64 emitter

Example   A five-cycle countdown iteration 
        LDX #$04
loop:   DEX          ; 2 cycles
        BNE loop     ; 3 taken / 2 not taken on the same page

The four iterations after LDX take 19 cycles and finish with X=0 and the zero flag set. A recognized loop can batch iterations while the available cycle budget covers them. The dispatcher can resume with the remaining iterations when a device event falls inside the full loop.

Interpreter mode disables native compilation and still uses direct dispatch and loop batching. Regular and Ultrafast also fall back to interpreter execution when native code is unavailable.

PPU events, scanlines, and pixels

The PPU tracks a 341-dot scanline and a nominal 262-line NTSC frame. The visible picture occupies 256 × 240 pixels. The core advances to events such as status changes, scroll reloads, and mapper IRQ clocks. Rendering can group consecutive elapsed scanlines when their inputs allow it.

Incremental caches retain decoded CHR rows and rendered row data. Cache checks include scroll, mapped CHR identity, and relevant memory revisions. Writes to scroll, palette, nametables, CHR banking, or sprite configuration can change which rows remain reusable. Sprite-0 overlap also feeds the PPU status register, so the core can resolve that timing when code polls $2002.

Regular and Interpreter retain NES palette and emphasis information until conversion for display. Ultrafast writes RGB565 directly and can defer eligible raster updates. Mid-scanline effects are modeled with targeted timing and rendering approximations.

Source files ppu.c, ppu_writes.h

Audio generation and DMC fetches

The base APU generates two pulse channels, triangle, noise, and DMC. All modes use fixed-point mixing at 48 kHz. Channel levels feed separate nonlinear lookup tables for the pulse pair and for triangle, noise, and DMC. The mixer applies filtering and converts the result to signed 16-bit PCM. Short-period waveforms can use averaging to reduce aliasing, with filtering choices that depend on the mode and active channels.

No-Lag changes the clock relationship

No-Lag can insert 100 post-render scanlines before vblank. The CPU and PPU clocks are scaled to retain the approximately 60.10 Hz frame cadence, giving the game more CPU cycles per displayed frame. Audio pauses during the added interval to preserve pitch. The NMI-to-picture distance retains its NTSC dot count. CPU-timed mapper IRQs and disk transfers follow the CPU clock.

Source files apu.c, apu_fixed.h, machine.c, sunsoft5b.c

Cartridges, mappers, and disk I/O

The loader uses the iNES or NES 2.0 header to select a mapper and submapper. A mapper can change the CPU’s PRG windows, the PPU’s CHR and nametable mappings, writable memory access, IRQ scheduling, and expansion audio. FDS uses a BIOS and drive model with writable program RAM, disk transfer registers, automatic side selection, and a disk save alongside the original image.

Example   The same PC can point to different code

A mapper register write can replace the PRG bank under $8000. A native trace cached for the previous bank cannot be selected solely by that CPU address. The core uses the mapped code identity for lookup. In FDS program RAM, a write can instead change the bytes in place. Writes to compiled bytes invalidate the affected traces, and runahead isolates writable code and disk state from the live machine.

Source files cartridge.c, mapper_writes.h, fds.c, supported mapper list

Input, runahead, and display

NES games choose when to latch their controllers. SDL supplies fresh button state through a callback when the emulated game latches input. Subsequent serial reads consume the latched bits. In the interactive loop, SchNES submits the live frame’s audio before any display wait and starts runahead close to the intended presentation time.

The prediction copies mutable state and can reuse compatible cached data. A two-frame prediction holds its first controller sample for the second speculative frame. The application can skip a presentation to catch up, and bypasses runahead in fast-forward and CPU raster view. It counts committed emulation frames and visible gameplay presentations separately.

The headless path renders full-size frames and generates audio without display pacing. Replay-and-hash tools check core changes against recorded inputs and a baseline. Timing tools can compare throughput and frame-time tails on those same inputs. Release publishing builds the lean static SDL application and uses profile-guided optimization where configured. That host build optimization is separate from the runtime 6502 recompiler.

./build/SchNES --headless 3000 game.nes
